01 · Decision

结论与当前边界

PVE 后端不再作为待验证能力处理，而是作为 Portage Engine 的 reference backend。下一阶段不应继续分散精力证明“VM 能不能拉起”，而应把已有成功路径固化成可重复回归，并优先修复社区化所需的信任与状态问题。

已确认：Terraform 创建 PVE VM、部署 Native Gentoo builder、执行 emerge 构建这条主链路已经在真实环境完成验证。后续阶段 0 仅做测试固化和版本基线记录。

  • P0-B 已实施：builder 只产 unsigned GPKG；独立 outbound-pull signer 通过 PostgreSQL digest-bound queue 签名，签名后再次由 Portage 强制验签安装，server/builder 均不挂载私钥。

退出标准：任意已发布 profile 都能只依赖已批准的内网对象重新烘焙，通过启动/Portage/build smoke，并由调度器选择匹配的不可变模板；禁用外网后不会发生隐式回源。

阶段 2｜持久化任务控制面

3–4 周 · PostgreSQL 事实源 + 可降级 Redis 协调层
  • DB-4 / P0-A + P0-B + SEC-1 + IAM-0 至 IAM-1G + SCHED-1 至 3 + MON-1 已实施：PostgreSQL schema v26 是 job、attempt、lease/fence、日志、infra cleanup lease、artifact、signing task、factory evidence、federated subject/session/revocation、project membership/policy、attempt resource/phase/runtime reservation、durable phase work/execution context、Worker Gateway session/command/upload、workload issuer/certificate lifecycle、artifact generation budget、executor capability、project fairness、worker score decision、capacity pool/action/instance、target history/SLO/cost projection、审计与 runtime setting 的唯一在线事实源；数据库模式不再读写 JSON job snapshot。每个新 job 记录 project、requesting subject、minimum executor protocol 与 exact all-of capability labels，数据库拒绝旧控制面 binary 或能力不匹配 executor 抢占并降级新安全契约。
  • DB-2 已实施：统一状态机使用 FOR UPDATE SKIP LOCKED 原子 claim、30 秒 lease、fencing、过期回收、cancel/retry 与终态发布校验。
  • DB-2 已验证：两个 control-plane replica 并发处理 40 个任务，每个任务只有一个 attempt；多 worker contention、lease expiry、stale completion 与 retry exhaustion 均有真实 PostgreSQL 测试。
  • DB-3 已实施：worker slot identity、infra ownership/remote-state pointer、artifact digest/lineage、factory run/step/evidence 均与 attempt/fence 绑定。
  • CACHE-0 已实施：Redis 只承载 control-plane presence TTL、分布式限流、scheduler wake-up 与 SSE fan-out；PostgreSQL 轮询是断线降级路径，Redis 不保存 canonical 状态。
  • DB-4 已实施：非敏感 cloud setting 在 PostgreSQL 中版本化并写审计事件；credential 只允许通过环境/secret provider 注入，WebUI 在数据库模式拒绝持久化 secret value。
退出标准：两台 control-plane replica 能并发提交和 claim，server/Redis/builder 在任意阶段重启后任务可继续跟踪或安全重试，不超卖 slot、不产生重复 attempt 或重复发布；PostgreSQL 不可用时停止接收 mutation 和新 claim，Redis 不可用时仅实时 UI/缓存降级。

阶段 2A｜项目矩阵、容量调度与运营 Monitor

2–3 周 · OBS 风格可见性与公平调度
  • 引入稳定的 project_id 与服务端解析的 target_id；target 由 desktop/base、systemd/OpenRC、architecture、libc、profile/image generation 等维度组成，不信任客户端任意标签。
  • 调度先按 arch、profile/image、build mode、能力和安全策略做硬匹配，再按空闲 slot、CPU/内存/磁盘压力、clean image/cache locality、排队时长和项目公平性评分。
  • 增加 global/provider、project、target 与 worker 四层并发/配额；把 VM provisioning 并发与实际 build slot 分开限流，避免云 API 抖动占满构建容量。
  • 建设项目矩阵 Monitor：项目/目标状态、24h/7d/30d 成功率、队列深度与最老任务、阶段耗时、失败分类、worker 空闲槽位/负载/heartbeat age，以及 job → attempt → worker → artifact/evidence 下钻。
  • 事件投影生成 Monitor read model；浏览器使用 SSE 接收增量并保留轮询降级。Prometheus 只使用低基数标签，job/package/revision 明细进入 PostgreSQL、结构化日志与 evidence store。
退出标准：desktop/base × systemd/OpenRC 等已发布目标能在同一页面独立展示状态和成功率；空闲/繁忙/离线 worker、容量、queue age、调度/重试原因均可解释；压测中不超卖 slot，且小项目不会被长队列永久饿死。

阶段 2B｜多 Worker 与分布式编译池

2–3 周 · job 并行 + MAKEOPTS + 可选 distcc
  • 明确三层并行预算：多个 job 在不同 builder 并行、单 job 的本地 MAKEOPTS、以及只承担编译任务的 distcc slots；三层都由 scheduler 原子预留，不能各自按 CPU 数独立超卖。
  • distcc pool 由服务端按 architecture、CHOST、compiler/version digest、toolchain image generation、CPU feature、network zone 与 tenant/project trust domain 严格分组；不匹配时必须 local fallback 或 blocked，绝不跨池静默执行。
  • 编译节点不持有 Portage repository、PVE/PBS token、builder token、binpkg/signing key 或发布权限；distccd 仅监听隔离构建网段，并用 firewall/allowlist 限制到已租约 builder。
  • 尊重 ebuild 的 distcc 限制，默认不启用 pump mode；先对 reviewed C/C++ 大包 allowlist 开启，小包以及 Rust/Go/Java、configure、link、test 仍在 job builder 本地运行。
  • 记录 local/remote compile 数、命中率、fallback、网络字节、队列时间和失败原因；以纯本地 clean build 为基线做差异与安装/GUI 回归，distcc 失败不得污染 staging 或直接发布。
退出标准：同一 locked profile/toolchain 下，2 个以上 job 可并行且单个 reviewed C/C++ workload 能安全借用 distcc pool；资源不超卖、断开任一 compile worker 可控降级、产物仍经过同一 staging/verify/promotion Gate，并保存 local-vs-distcc 对照证据。

02A · State Platform

PostgreSQL 与 Redis：职责必须分开

DB-4 / P0-A + P0-B + SEC-1 + IAM-0 至 IAM-1G + SCHED-1 至 3 + MON-1 已完成在线状态切换：PostgreSQL schema v26 是控制面、signing queue、federated subject/session/revocation、project membership/policy、active-attempt resource/phase/runtime reservation、durable phase work/execution context、Worker Gateway session/command/upload、artifact generation budget、executor capability routing、project fairness、worker score decision、capacity action/instance 与 target history/SLO/cost projection 的事实源，Redis 是可整体清空的加速层。数据库模式下 Broker 只做 HTTP 适配，不再持有不可恢复的执行权威；旧内存路径只保留给完全禁用数据库的单机兼容运行。PHASE_EXECUTOR_MODE=active 时只启动 admission + 独立 phase worker，不再启动 legacy whole-pipeline executor。

PostgreSQL 是必须项

  • 作为 job、attempt、lease、artifact、infra lifecycle、catalog version 和 audit event 的唯一事实源。
  • 依靠唯一约束、行锁、版本号和事务保证幂等、状态机与 slot reservation。
  • 使用 transactional outbox 产生可重放事件，Monitor/read model 可以删除后重建。
  • 控制面多副本共享同一状态，不再依赖某个进程内的 map 或 channel。

Redis 不能成为事实源

  • 不把 build queue、canonical lease、发布状态、审计或唯一日志放在 Redis。
  • 不使用 Redis Pub/Sub 承诺可靠交付；断线消费者会丢失消息。
  • 不使用无 fencing token 的分布式锁保护 VM、worker slot 或 artifact promotion。
  • Redis 故障必须可降级为 PostgreSQL 查询、轮询和本地保守限流。

事务与租约规则

  1. 提交：(project_id, idempotency_key) 唯一；同 key 同 digest 返回原 job，不同 digest 返回 conflict。
  2. Claim：在短事务中筛选 eligible job、FOR UPDATE SKIP LOCKED、创建 attempt/lease、预留 slot、递增 fence 并写 outbox，然后提交；VM 创建和 HTTP 调用不得放在数据库事务内。
  3. 状态转换：UPDATE ... WHERE id=? AND version=? AND state IN (...)；影响行数为 0 表示 stale actor，禁止覆盖新状态。
  4. 续租/完成：同时校验 attempt、worker、lease state、expiry 和 fence；旧 worker 即使恢复网络也不能完成或发布已重新分配的 attempt。
  5. 制品发布：采用 prepare → external atomic move/CAS write → finalize 的 saga；每一步有幂等 operation ID 和 reconciliation。不要假装 PostgreSQL 事务能与 NAS/PBS 文件移动形成原子两阶段提交。
  6. 事件：业务行与 outbox 同事务写入；projector 幂等消费。LISTEN/NOTIFY 或 Redis Pub/Sub 只发送“有新 outbox row”的提示，消费者始终能从 PostgreSQL cursor 补读。

仓库已经有 PostgreSQL durable queue、project weighted fairness、queue-age 反饥饿、exact capability routing、worker heartbeat、pull-aware worker score ledger、按 catalog provider/zone/arch/profile/image generation 拆分的 capacity-pool、独立 fenced provider actuator，以及 24h/7d/30d target SLO/latency/cost read model；因此已经越过单进程 Alpha 调度。尚未闭合的是 target/provider pool 级公平、worker OS pressure/cache-locality telemetry、provider invoice 对账。SCHED-2B/3 与 MON-1 的代码、PostgreSQL、Prometheus 与 WebUI 已完成；真实 PVE create/drain/delete Gate 必须等待单独构建的 persistent-executor 模板，不能复用一次性 job builder 模板。

结论：当前已经能解释 project weight、反饥饿提升、capability mismatch、worker 候选数/压力/近期失败，每个 provider/profile/image pool 的 active/desired/backlog/blocked，以及 actuator action/instance 的 requested、claimed、provisioning、active、draining、deleting 与失败退避；也能按 target 回答最近 24h/7d/30d 的成功率、样本充分性、排队/运行 P50/P95、主要失败分类和内部预留/结算成本。仍不能回答 provider invoice 为何偏离内部估算，也没有把 OS pressure/cache locality 接入 worker 退避。

借鉴 OBS，但不复制 OBS 的全部复杂度

OBS 的 project 承载 repository、architecture 与调度参数；scheduling 与 dispatching 是两个概念；dispatcher 会把 job 分配给符合约束的空闲 worker，并按 project repository 的历史 build time 做公平共享。Portage Engine 当前规模不需要立即拆成 OBS 的多 daemon 后端，但数据边界应该从一开始兼容这三个原则：

  1. Project 是运营与策略边界：例如 base、desktop、experimental；后续可绑定 owner、优先级、配额、保留期与发布策略。
  2. Target 是可构建矩阵单元：由服务端 catalog 解析为不可变 tuple，而不是让用户提交自由文本标签。例如 desktop/amd64/systemd/glibc、base/amd64/openrc/glibc。
  3. Attempt 才是一次实际执行：一个 job 可因 infra/transient failure 产生多个 attempt；成功率、worker 归属、耗时和成本按 attempt 记录，项目最终状态按 job/pipeline 聚合，避免重试和远端副本重复计数。

Static Builder 环境洁净度与复用边界

Static 只能表示“调度 agent 长期在线”，不能表示“同一个可写 Gentoo root 长期复用”。当前 Native 路径虽然已有 job-scoped PORTAGE_CONFIGROOT、PKGDIR、workspace 和 --oneshot，但 emerge 仍会 merge 到宿主 /，修改 VDB、已安装文件、preserved-libs、服务与任意 ebuild postinst 状态；--oneshot 只是不把 atom 写入 world。事后执行 depclean、恢复 world 或删除 /var/tmp/portage 都无法证明恢复到原始字节状态。

多 Worker、Portage 并行与 distcc 设计

多 worker 要分成三个独立问题：多个 package job 的并行度、单个 job 在一台 builder 内的本地并行度、以及把 C/C++ 编译动作分发到 distcc pool。distcc 不是通用构建 worker，也不能替代 Portage、job workspace、链接、测试、签名或发布。

03 · Users & Delivery

用户形态、emerge 位置与组件分发

Portage Engine 不应该替代 Portage。普通用户的安装体验必须保持为原生 emerge；CLI 只补足“请求远端构建”这一项 Portage 原生没有的能力；builder 则属于 Infra 内部组件，不进入普通用户路径。

核心决定：消费 binpkg 不要求安装 Portage Engine CLI，也不要求启用 Portage Engine overlay。用户只需建立一次 binhost 与信任根，然后继续使用标准 emerge --getbinpkg。远端构建必须是显式操作，第一阶段不要把“binpkg miss 自动触发社区构建”挂进 emerge。
CONSUMER

普通 Gentoo 用户

只消费已经发布的 binpkg。无需 API token、CLI 或 overlay；公网默认使用 HTTPS binhost；受控内网也可使用 HTTP，但必须强制验证可信 Packages/GPKG 签名。

emerge --getbinpkg app-editors/foo
# 强制只用已发布二进制包
emerge --getbinpkgonly app-editors/foo
DEVELOPER

包开发者 / 高级用户

通过 CLI 或 Web UI 查看本机 build context，显式生成 BuildSpec、提交任务并观察验证结果；成功后仍然回到原生 emerge 安装。

pe build plan app-editors/foo --from-system
pe build submit --plan build.lock --wait
emerge --getbinpkgonly app-editors/foo
OPERATOR

社区 Infra 运维者

部署 control plane、builder image、signer、artifact store 和策略。builder 的安装、升级与密钥管理不暴露给普通用户。

pe-admin worker rollout --version 0.4.2
pe-admin signer status
pe-admin artifact promote <digest>

输入与构建

  • 同步区先解析并验签 Gentoo stable branch commit；runner 从锁定 bundle 创建 gentoo.git，让 master 与 plan 命名的本地 snapshot ref 都指向该 commit；禁用会触发远端更新的特殊 treeish stable，完整 commit 另行写入 manifest。

  • distdir 与 seed 由锁定的内网对象提供；首个 PoC 禁用 seedcache/pkgcache，Catalyst 两步均在无网络 namespace 中运行。

需要区分两种部署：mirror-backed offline 的构建区没有公网出口，但能访问内网镜像；strict air-gap 连同步网关也不可达，只能导入经过审批的签名 content bundle。两种模式使用同一 manifest。受控内网可使用 HTTP 数据面，但绝不能变成“裸传输”：host 必须在 lock allowlist，URI 不得携带凭证/查询参数，重定向关闭，对象仍按固定大小、SHA-256、上游 Manifest 或签名验证。项目自有的 server/dashboard 与 Desktop adapter 可在隔离可信 LAN 上先用 HTTP 走通，adapter 必须显式开启 -allow-http-control-plane，URL 仍禁止 credentials/query/fragment/path 与 redirect；此时 bearer/API token 在链路上是明文，只能作为 bring-up 模式。跨不可信网络前再升级为 HTTPS、VPN、mTLS 或 WireGuard/IPsec。PVE/PBS 继续复用产品自带的 HTTPS API，不需要为 Portage Engine 另签一套证书；现有 NAS 上传 API 的 HTTP + session password 仍是 trusted-alpha 风险例外，不能因为下载对象有摘要就认为登录凭证也安全。

离线构建的预检与同步闭环

  1. Resolve：在联网同步区用精确 profile/USE/keywords 解析 image 与测试包依赖图，生成 repo、distfiles、seed、binpkg、plugin/module 的完整对象清单。
  2. Fetch & verify：只从 allowlist 源抓取；校验 Git/GPG、Manifest、SHA256、Terraform lock 与 go.sum，记录许可证和 RESTRICT 例外。
  3. Bundle：对象按 digest 存储，清单签名；strict air-gap 对传输介质编号、恶意文件扫描并执行双人审批。
  4. Dry run：构建区关闭公网 egress，以 clean cache 运行 Catalyst、Packer、Terraform init 和代表性 emerge fetch/build。
  5. Freshness：记录上次成功同步与安全公告水位；超出 SLO 允许继续开发测试，但禁止 stable promotion。

不要把矩阵做成组合爆炸

模板只承载不能安全地在 job 中临时切换、或者会改变 ABI/基础运行时的边界。包级 USE、keywords、CFLAGS 和普通依赖选择属于不可变 BuildSpec；它们不应该产生新的 VM template。

architecture是amd64、arm64 等必须独立；builder binary 与 verifier 也必须匹配。
libc / ABI是glibc/musl、multilib/no-multilib 作为硬边界。
init / 官方 parent profile通常是systemd/OpenRC 以及 hardened 等基础 profile family 独立烘焙并测试。

自有 profile 与服务端 Registry

Profile repository

  • 单独维护 portage-engine-profiles，或至少与用户 CLI overlay 分目录、分权限；它属于构建策略，不属于客户端安装渠道。
  • 使用 repository profile 继承 Gentoo 官方 parent，只覆盖社区明确维护的 defaults、USE mask/force 与 package sets。
  • package set 使用独立、锁定的 catalog 作为跨 profile 复用层；BuildPlan 只选择 set ID，Packer 展开后生成 /etc/portage/sets/portage-engine-image。不要把常用工具抬进 @system。
  • 提交必须经过 pkgcheck、parent 可解析、emerge --info、depgraph 和升级测试；保护分支、签名 tag、双人 review。
  • 模板绑定 profile repo 的 commit/digest 与 Gentoo repo snapshot，不能在启动时追踪 latest。

05 · Desktop E2E

桌面 GUI E2E 要解决什么

目标不是简单“截图看看”，而是验证一个刚构建的 Gentoo binary package 在真实桌面环境中可以安装、启动、显示关键界面、完成核心交互，并在失败时保留足够证据。

适合桌面 E2E 的验证

  • 应用能否安装、启动并创建窗口。
  • 菜单、对话框、渲染区域和基本输入是否正常。
  • GTK/Qt/WebKit/Electron 依赖是否完整。
  • 不同桌面、分辨率、locale、显卡模式下是否工作。
  • 崩溃、黑屏、缺字体、缺图标、窗口未响应等视觉故障。

不应只靠视觉判断

  • 包是否安装成功：检查 emerge 退出码和 Portage DB。
  • 进程是否启动：检查 PID、systemd/user session 或 D-Bus。
  • 文件是否生成：直接检查 guest filesystem。
  • 崩溃原因：收集 coredump、journal、stderr 和应用日志。
  • 网络请求：通过代理、HAR 或服务端日志验证。
核心原则：能用结构化状态断言的，不用截图；能用可访问性树定位的，不用坐标；只有真正的视觉结果才使用 needle/像素比对；AI 作为最后一层语义判断和故障分析。

06 · Architecture

推荐架构：openQA 思路的混合方案

建议把桌面测试作为独立的 Desktop Verification Plane，不要塞进现有 builder 进程。Portage Engine 负责调度和制品状态，GUI runner 负责 VM 生命周期、输入、截图和断言。

1. BuildNative Gentoo 构建并上传 staging
2. Schedule创建 desktop verification job
3. Restore从干净桌面快照启动 VM
4. Install配置 staging binhost 并安装包
5. Exercise启动应用并执行 GUI 场景
6. Judge结构化 + 视觉 + AI 分层判定
7. Promote通过后签名并原子发布
控制面

Portage Engine job state、policy、artifact digest、测试矩阵和 promotion gate。

GUI Runner

创建/恢复桌面 VM，驱动场景，收集截图、视频、串口、journal、coredump 和测试结果。

控制通道

QMP/libvirt/PVE API 管生命周期与截图；VNC/SPICE 注入键鼠；SSH/virtio-serial/guest agent 执行确定性命令。

定位与断言

Accessibility tree/AT-SPI → openQA needle/模板匹配 → OCR → 视觉 AI。

测试环境

固定 desktop image、字体、主题、DPI、分辨率、locale、时区和 GPU 模式；每次从已知快照恢复。

openQA、Playwright 还是自研？

方案最适合优点限制建议
openQA / os-autoinst 完整 OS、桌面、安装器、原生 GUI VM、VNC、串口、needle、失败证据和人工更新基线都比较成熟 系统较重；测试 DSL 和运维体系需要学习 首选参考实现；可以独立部署，由 Portage Engine 调度 job
Playwright Web UI、WebView、Electron renderer DOM/ARIA 定位稳定，trace、截图 diff、视频生态成熟 不能通用控制 GTK/Qt 桌面，也无法覆盖系统安装器和原生对话框 测试 Dashboard 和 Web/Electron 应用时使用，不作为通用桌面控制层
轻量自研 runner 与 PVE 深度集成的有限应用矩阵 能复用现有 PVE、job model 和 artifact pipeline 需要自己实现稳定等待、needle、视频、调试 UI 和基线管理 先做 MVP；如果测试矩阵快速增长，逐步采用 openQA 而不是重写它
推荐落点：Portage Engine 保留 PVE 作为构建后端；新增专用 GUI test worker。早期可以在 PVE 上恢复预制桌面 VM 并使用自研 runner；场景数量变多后，将 openQA 作为独立验证服务接入，Portage Engine 只传入 staging binhost、artifact digest 和 scenario 参数。

08 · AI & MCP

要不要引入视觉 AI 和 MCP？

要引入，但放在增强层

  • 探索未知应用的首次操作流程。
  • 识别弹窗、黑屏、布局破坏和异常渲染。
  • 分析 expected/actual/diff 与日志，给出失败分类。
  • 从成功运行中生成候选 needle、OCR 区域和测试步骤。
  • 跨小版本 UI 变化时做语义相似判断。

不要让 AI 成为唯一测试 oracle

  • 模型输出存在非确定性，难以复现边界结果。
  • 成本和延迟不适合每个截图、每个步骤调用。
  • 视觉模型可能忽略小但关键的错误。
  • 模型或 prompt 升级会改变历史基线。
  • 涉及桌面控制时必须限制工具权限和网络边界。

MCP 的正确角色

MCP 适合作为 AI Agent 与 Desktop Runner 之间的标准工具接口。它不负责任务持久化、基线管理、重试或发布判定；这些仍由 Portage Engine 和 GUI runner 完成。

MCP Tool职责安全约束
desktop.screenshot返回当前屏幕或指定区域 PNG只访问当前测试 VM
desktop.click按坐标、needle 或 accessibility node 点击记录每次输入；禁止宿主操作
desktop.type输入文本或组合键限制长度，敏感字段不回传日志
desktop.wait_for等待窗口、needle、OCR 或稳定画面强制 timeout
desktop.accessibility_tree读取当前桌面语义树只读，限制节点数量
guest.exec在 guest 中执行诊断/安装命令命令 allowlist 或测试角色授权
vm.restore_snapshot恢复到已知桌面基线只能选择测试项目允许的快照
test.attach_evidence保存截图、日志和 Agent 结论绑定 job ID 与 artifact digest
与 Playwright MCP 的差别：Playwright 能读取 DOM/ARIA，因此 Web UI 的定位非常稳定；原生 Linux 桌面没有统一 DOM。你的 Desktop MCP 需要把 VNC/QMP 截图、键鼠输入、AT-SPI accessibility、OCR 和 guest 命令组合起来，才能达到类似体验。

推荐的 AI 执行模式

  1. Deterministic run：正常回归只执行固定步骤与断言。
  2. Failure triage：失败后才调用视觉模型，输入最后若干截图、diff 和裁剪后的日志。
  3. Exploratory run：对新应用由 Agent 使用 MCP 探索，产出符合严格 schema、可审查的 JSON 场景和 needle 候选。
  4. Human approval：人审查并提交测试脚本/基线；后续回归不再依赖 Agent 自由决策。

GUI-1 runner 与真实 PVE Gate 已通过（2026-07-26）：新增独立 portage-desktop-runner 与严格 JSON scenario schema；action 只允许 restore/start、staging install、application ID 启动、accessibility wait、受限键鼠、reviewed needle、screenshot/accessibility/log collection 和 stop，不接受任意 shell command 或 credential 字段。runner 既可连接独立 adapter（默认 HTTPS；隔离可信 LAN 可显式开启 HTTP bring-up），也可直接调用已有 PVE HTTPS API，并通过 QEMU Guest Agent 暴露的命名 helper 执行受限动作，因此不要求再部署一套 HTTPS console 服务。HTTP adapter 不接受 URL credential/query/fragment/path，不跟随 redirect，但 bearer token 在链路上仍是明文。PVE 现场没有通用 agent/file-read 路由，证据改为在受限 helper 中先返回大小与 SHA-256，再经支持的 QGA exec 以最多 192 KiB 分块读取；host 限制单件 32 MiB、拒绝截断并复验完整摘要。应用日志只读取该应用对应的确定性 user unit，AT-SPI 树限制 4096 节点并校验 parent/index。应用 staging 可以走无凭证的只读 HTTP，但必须先固定完整 MANIFEST.json digest，禁用代理和跨站 redirect，再逐对象验证大小与 SHA-256，最终切为本地 file:// binrepo。PVE token 只从环境变量读取；runner 要求唯一 restore/start/stop，功能步骤首次失败后停止继续输入，但仍执行声明的 screenshot/accessibility/log evidence，并始终尝试最终 stop。固定 1280×720、LightDM 自动登录、C.UTF-8、字体/主题、AT-SPI、截图及键鼠工具已经进入 desktop image Gate。真实 VMID 145 candidate 的 disposable clone 已通过完整 scenario：XFCE 桌面与终端可见，稳定 selector 为 role=terminal,name=Terminal，截图、AT-SPI 和应用日志均按摘要复验。视觉 AI 只保留为未来 triage 助手，不作为 release oracle。
